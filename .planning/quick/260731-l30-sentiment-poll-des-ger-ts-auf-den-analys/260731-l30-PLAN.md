<critical_finding>
## Die ursprüngliche Lösungsidee funktioniert so nicht — bitte vor dem Coden lesen

Die Aufgabenbeschreibung geht davon aus, `next_update_minutes` sei ein Countdown bis zur nächsten Analyse. **Das ist nicht der Fall.**

In `sentiment-api/moodlight_extensions.py` (Zeile 89-98):

```python
def _get_next_update_minutes() -> int:
    worker = get_background_worker()
    if worker is not None:
        return max(1, worker.interval_seconds // 60)
    return 30
```

Der Wert ist also **konstant** das Worker-Intervall (immer `30`) — völlig unabhängig davon, wann die letzte Analyse tatsächlich lief. Live-Abruf bestätigt das: `"next_update_minutes":30`.

Würde man wie vorgeschlagen auf `next_update_minutes + 90s` pollen, ergäbe das einen freilaufenden 31,5-Minuten-Timer. Der wäre **länger** als der Server-Takt von 30 Minuten und würde deshalb langsam immer weiter zurückfallen — der Zustand würde also schlechter statt besser.

**Das nutzbare Signal ist stattdessen das Feld `timestamp`** — der echte Zeitpunkt der letzten Analyse (`latest['timestamp']`, Zeile 179). Damit lässt sich die tatsächliche Restzeit ausrechnen:

```
Restzeit = (timestamp + next_update_minutes) - jetzt + Puffer
```

Beispiel: Analyse lief vor 22 Minuten, Intervall 30 Min → nächster Poll in 8 Min + Puffer statt in 30 Min. Genau das synchronisiert das Gerät auf den Server-Takt.

Wichtig zur Alterung des Werts: `/api/moodlight/current` hat einen 5-Minuten-Redis-Cache, der Worker invalidiert ihn aber bei neuen Daten sofort (`_invalidate_moodlight_cache()`). Ein `timestamp` aus dem Cache ist also nie neuer als die letzte echte Analyse — die Rechnung bleibt korrekt.

Da die Firmware die Uhrzeit nicht zuverlässig zur Verfügung hat (NTP kann fehlen), wird der `timestamp` **nicht** gegen die lokale Uhr gerechnet, sondern über das ebenfalls gelieferte Feld `age_minutes` bzw. — falls nicht vorhanden — über den ISO-Zeitstempel. Siehe Task 1 für den konkreten, robusten Weg ohne NTP-Abhängigkeit.
</critical_finding>

`unsigned long nextMoodPollDelay = 0;` mit deutschem Kommentar, dass 0 "kein Serverwert vorhanden — Fallback auf moodUpdateInterval" bedeutet.

In `sensor_manager.cpp` drei Stellen ändern:

**(a) Intervall-Check (Zeile 264).** Vor dem Check das wirksame Delay bestimmen: eine lokale `unsigned long effectiveDelay = appState.nextMoodPollDelay > 0 ? appState.nextMoodPollDelay : appState.moodUpdateInterval;` und der Check nutzt `effectiveDelay` statt `appState.moodUpdateInterval`. Die bestehende Oder-Bedingung `|| !appState.initialAnalysisDone` bleibt unverändert, damit der erste Abruf sofort läuft. Auch das Debug-Log in Zeile 239 auf `effectiveDelay` umstellen, sonst zeigt es einen anderen Wert als den tatsächlich benutzten. Achtung: Zeile 239 liegt in einem eigenen Scope weiter oben — dort separat berechnen oder die Berechnung vor Zeile 239 ziehen.

**(b) Berechnung nach erfolgreichem Fetch.** Im Erfolgszweig (nach Zeile 352, wo `initialAnalysisDone` gesetzt wird) das nächste Delay aus der API-Antwort ableiten:

- `next_update_minutes` als int lesen; fehlt das Feld oder ist es `<= 0` oder `> 1440` (24h) → `appState.nextMoodPollDelay = 0` (Fallback) und Debug-Hinweis loggen.
- Alter der Analyse bestimmen: Aus dem Feld `timestamp` (ISO-8601-String, z.B. `2026-07-31T13:02:49.203106+00:00`) das Alter zu berechnen erfordert eine gültige lokale Uhr. Deshalb defensiv: Nur wenn `appState.timeInitialized` true ist, den Zeitstempel per `strptime()` in eine `struct tm` parsen, mit `timegm()` in `time_t` wandeln und gegen `time(nullptr)` das Alter in Sekunden bilden. Ist `timeInitialized` false oder schlägt das Parsen fehl → Alter als 0 annehmen (dann verhält es sich wie bisher, nur mit Puffer).
- Alter auf einen plausiblen Bereich begrenzen: negatives Alter (Uhr-Drift) auf 0, Alter größer als das Intervall auf das Intervall.
- Restzeit `remainingMs = (intervalMinutes * 60000UL) - (ageSeconds * 1000UL) + POLL_BUFFER_MS`, wobei der Puffer 90000UL (90 Sekunden) beträgt, damit die Server-Analyse sicher durch ist.
- Untergrenze erzwingen: mindestens 60000UL (60 s), damit ein Serverwert von 0/1 Minute keine Poll-Schleife erzeugt.
- Obergrenze: nie mehr als `appState.moodUpdateInterval`, damit der konfigurierbare Wert die Obergrenze bleibt (Anforderung aus der Beschreibung).
- Ergebnis in `appState.nextMoodPollDelay` schreiben.

Die beiden Konstanten (Puffer 90000UL, Minimum 60000UL) als `static const unsigned long` lokal in `sensor_manager.cpp` definieren, nicht in `config.h` — sie sind reine Implementierungsdetails dieses Moduls.

**(c) Fehlerzweig und Abschluss-Log.** Im Fehlerzweig (ab Zeile 367) `appState.nextMoodPollDelay = 0;` setzen, damit bei API-Ausfall garantiert das konfigurierte `moodUpdateInterval` gilt — die bestehende Fehlerlogik (Zähler, Neutral-Modus, Status-LED) bleibt sonst komplett unangetastet. Das Abschluss-Log (Zeile 406) muss das tatsächlich wirksame Delay ausgeben, also erneut `nextMoodPollDelay > 0 ? nextMoodPollDelay : moodUpdateInterval` in Sekunden.

Kommentare und Log-Texte auf Deutsch mit korrekten Umlauten, Bezeichner auf Englisch (Projektkonvention). Kein Version-Bump in `config.h` — Release macht der Orchestrator.
